# Agent profiles and bounded delegation

Studio provides an **Agent Designer** at `/agents` for creating, organizing, versioning, and deleting local agent-profile revisions. A profile pins a host-configured provider and version, system instructions, optional reasoning/output-token settings, selected MCP tool contracts, exact text-skill snapshots, and optional coordination-channel memberships. Saving changed behavior creates another immutable version; moving a profile between folders changes only local organization.

In the workflow designer, select an agent node and assign the exact profiles it may call under **Subagents**. The profile revision and its skill snapshots are embedded in the workflow. Profiles do not contain credentials, server endpoints, or host grants. Exported packages list provider, MCP tool, profile, and skill requirements, but a consuming application must register those dependencies and explicitly authorize MCP tools itself.

At runtime, assigned profiles appear to the parent model as bounded `delegate` tools. The parent supplies a task string and receives a result string. The child uses its profile's instructions, provider, skills, reasoning/output settings, and tool list. A child does not inherit the parent's tools. Each requested child MCP tool must also be allowed by the host policy for the parent workflow node; failure to resolve or authorize a required tool fails that delegation closed.

The initial delegation implementation is deliberately bounded:

- A parent may expose at most four profiles and make at most four delegation calls during its node invocation.
- Delegation depth is one level; profiles cannot delegate further.
- Each task is limited to 16,384 characters. Agent calls retain the existing provider timeout and model-round limits.
- A profile's optional output-token limit applies to that child agent. There is no aggregate token budget across the parent and children yet.
- Child model, tool, start, completion, and failure events retain the same run/revision and use a distinct child invocation ID. Event data identifies the exact profile revision and links child activity to the parent invocation. Playback reads this evidence and makes no live calls.
- The parent model chooses which assigned delegate tool to call and when, so it can run bounded sequential turns. Persistent agent memory, workflow-as-tool invocation, automatic retries, and model-selected tool-call approval are outside the current scope.

When an agent node has two or more assigned profiles, its parent also receives a **parallel team** tool. One task is sent to every assigned profile concurrently, up to four members. The team returns a JSON array in assignment order, with each member's profile ID, version, name, and output. Individual delegation and team calls share the four-child-execution limit for that parent invocation. If one member fails, the team cancels remaining members where possible, records a failed team event, and returns no partial aggregate; the parent model may decide how to proceed from the tool error. Completed MCP side effects are not undone. The combined result is limited to 80,000 characters.

In Agent Designer, enter up to eight coordination channel IDs on a profile, one per line. When a parent calls a delegate or a parallel team, each child receives `channel_send` and `channel_read` only for its pinned memberships. IDs use lowercase letters, digits, dots, hyphens, and underscores. Profiles pinned to the same ID can read its append-only messages; membership in another channel is rejected. A message is at most 4,000 characters; each channel holds at most 32 messages and each board at most 64. Sequential delegate turns share a board scoped to that parent agent invocation. A parallel team call uses its own board, isolated from sequential turns and other team calls. Every send and read is recorded with the child invocation, and read evidence includes the exact messages returned to that model. Playback reconstructs the exchange without model calls. Persistent memory and aggregate token/time budgets are not implemented.

The local Agent Designer library is part of the unauthenticated development Studio and is stored in its data directory. It is not a multi-user asset service. Consumer hosts do not need this local library to execute a package because each used profile revision is embedded in the workflow definition.

See the [user guide](user-guide.md#design-reusable-subagents) for the Studio workflow and [architecture](architecture.md#versioned-agent-profiles) for runtime boundaries.

VAW uses the explicit specialist-as-tool shape for this first increment; it does not take a dependency on the OpenAI SDK.
