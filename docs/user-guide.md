# Studio user guide

The Studio creates and runs linear and conditional workflows, up to four sequential two-branch blocks in schemas 1.14–1.31, and one configurable 2–8 branch region in schema 1.32. It also supports one bounded linear-body loop and bounded Boolean decision graphs, with bounded text and JSON input. Deterministic transforms and text templates, workflow-owned typed scalar parameters, host-approved MCP tools with bounded structured JSON inputs, a deterministic demonstration agent, and opt-in host-configured external model providers are available. Templates combine the incoming string with declared parameters using explicit tokens; they do not provide expression evaluation. JSON input can be reduced to text with a pointer selector or mapped into a bounded JSON object with the **Project JSON fields** node. This is an explicit static projection, not a general-purpose mapping language or dynamic object port system. The typed graph preview grows in opt-in schema steps: schema 1.23 enables separate execution/data pins and pure text values; schema 1.24 adds typed Boolean comparison and branching; schema 1.25 adds Boolean constants and NOT; schema 1.26 supports bounded nested branches, reconvergence, and multiple termination exits; schema 1.27 supports embedded pure graph functions. Studio includes a local Function library and graph editor for immutable function revisions, with exact snapshots embedded in workflow call nodes. Free placement and wire routing organize the graph; only explicit control nodes change execution semantics.

Use the **Theme** selector in the top navigation to switch between **Dark Modern**, **Light Modern**, **VS Code Dark+**, **Solarized Dark**, **Nord**, **Monokai**, **GitHub Dark**, **GitHub Light**, **Dracula**, **Neon Glow**, **Retro Drive**, and **High Contrast**. Retro Drive uses a smoked-black instrument-panel palette with amber indicators, cyan display traces, and warm ivory text. The Studio remembers the choice in this browser and keeps it when you move between the designer, settings, and observation pages. The graph canvas and nodes use colors coordinated with the selected shell theme. The graph opens at 100% zoom; **Fit graph** frames the nodes when needed. Its grid fills the viewport and tracks pan and zoom. Embedded hosts can customize inherited theme tokens independently; see the [editor design system](design-system.md).

All Studio pages share the same IDE shell, project selector, theme selector, active-page indication, content surface, and responsive spacing. The Explorer and activity bar navigate project assets. **Studio settings** in the title bar contains user-specific MCP and model connections; these host credentials do not belong to a project. At phone widths the navigation wraps and page content reflows; the graph itself keeps its own scrollable viewport. The same checks run across every Studio route at normal size and at 200% text size.

Use disposable text in the local development app. It records inputs, outputs, and comments in local storage without workspace authentication or payload encryption.

When you open a project workflow, the editor loads the saved graph first. MCP tool and model-connection choices load independently after the interactive editor opens, so a slow or unavailable endpoint does not hold the graph behind a blank page or prevent the other choice list from loading. The document status bar summarizes loading; if discovery fails, the draft stays editable and **Problems** provides a retry action. Recorded run history loads in the background in **Runs**. Folder projects use the same independent, non-blocking loading behavior for their agent profile and graph editors.

Studio connection tests distinguish endpoint errors from stdio executable/process failures. A stdio process that exits before MCP discovery reports checks for its executable, arguments, working directory, and server logs; configured environment values are not included in that diagnostic.

## Work in a workflow document

Starting a saved workflow from **Run workflow** opens the run inspector automatically. Use **Back to workflow** to resume editing; use **Inspect** in the Runs panel to reopen a prior run. If the interactive server connection drops, Studio keeps the graph visible behind a compact, theme-aware reconnect status toast instead of covering the workspace with a blocking white dialog; retry controls remain available when the connection cannot be restored automatically.

The project workflow editor uses document tabs, a canvas, and a contextual inspector. Choose a workflow in Explorer or an open document tab; Explorer keeps the active file highlighted. The document header provides **Save**, **Run workflow**, and **Workflow settings**. **Run workflow** opens a dialog for test input and typed workflow parameters, then starts the saved workflow with those values; it does not publish or activate a revision. The settings drawer overlays the editor and contains workflow naming, parameters, discard, reuse, and import/export tools without moving the canvas. Create workflows from the Explorer's **workflows** folder context menu. Close a document with its **×** button or middle-click its tab. Closing an unsaved document asks whether to keep it open or discard its edits; closing a clean inactive tab leaves the active editor untouched.

The graph editor offers node duplication, typed template insertion, and bounded clipboard actions from a node's context menu. **Copy selected pure data nodes** uses the existing box/Ctrl/Shift selection when the context-menu node is selected; it preserves internal typed edges, external data boundaries, per-node layout, and fresh IDs. Ctrl/Cmd+C and Ctrl/Cmd+V invoke the same actions; keyboard paste places the fragment at the canvas center. **Paste pure data node here** remains limited to explicit typed graphs. Execution flow, capabilities, mutable state, annotations, and cross-workflow dependency metadata are not copied.

Use **Select** to drag a selection rectangle on empty canvas, or **Pan** to move the view; middle-drag also pans. Click the graph overview to navigate. Selecting a node opens its **Configure** view; **Inputs** and **Outputs** describe its actual typed pins. The inspector scrolls independently of the canvas.

The lower panel has **Runs**, **Output**, and **Problems**. After starting a run from the input dialog, **Runs** shows recorded status, workflow, start time, duration, and run ID. Choose **Inspect** for the execution graph and **Back to workflow** to resume editing. **Output** shows the selected or latest started run's recorded result. Direct runs of an unchanged saved catalog workflow capture its graph layout for playback; later edits do not move or rename nodes in that recorded view. **Problems** lists graph issues and connection-discovery failures, with an MCP retry action. A draft with graph issues can be saved. **Run workflow** remains available for a saved draft so an explicit attempt can explain the block in **Problems**, but no run is started until every graph issue is resolved. Connection discovery runs in the background and is summarized in the document status bar.

## Organize work with projects

Open the project switcher in the title bar and choose **Manage projects…** to create a project, archive it, or restore it. Use the same switcher to change the active project. The workflow editor, Agent Designer, Skill library, and Function library follow the selected project. The first project is **Default Project**; when an older Studio data directory is opened, the Studio copies its workflow catalog and skill/profile/function files into this project and keeps the original files as a recovery copy.

Projects organize local authoring. Model provider and MCP connection settings remain environment-wide because they contain endpoints, credentials, and host registrations. Choosing a tool in a project does not grant it permission; the current development host still applies its local broker policy. Run history is also host-wide. Archived projects are omitted from the selector, and their data is retained; restore an archived project from **Projects** to open it again.

On **Projects**, choose **Download source snapshot** for a deterministic ZIP containing workflow and asset JSON with a manifest and content hashes. You can **Import as new project** to restore a validated snapshot into a separate catalog-backed Studio project; it does not merge with or replace an existing project. To work directly in Git source, choose **Open folder** in Explorer and enter the absolute path to a validated project folder. The folder is added to the project switcher and project list and opens in a project tab. Click the folder/name button in the titlebar to search projects by name or folder path; paths distinguish projects with the same name. Use Arrow Up/Down and Enter to choose, Escape to cancel, or the separate **Open folder…** and **Manage projects…** links. Highlighting or filtering never changes projects. Open up to eight folders together, then switch tabs to move between their independent trees and editor buffers. With a folder already open, expand **Open folder** in the project header to add another; the bounded form works on narrow screens and closes after the selected project changes. Tab order and selection persist in Studio-local settings; unsaved buffers stay in the current browser session and are not recovered after refresh or restart. The project explorer groups manifest-indexed files by directory. Select a workflow file to open it in the graph editor, a skill to create a new immutable revision with a typed form, an agent profile to create a new immutable profile revision, or a graph function to edit its typed interface and pure graph. Saving adds a content-addressed source file and updates the project manifest; older versions remain unchanged. Profile requirements for model connections and MCP tools remain logical IDs, not copied credentials or grants. Folder workflows can use project skills, agent profiles, and graph functions alongside the host's configured providers and MCP bindings. Graph-function edits are saved as new immutable project revisions; the selected file and any workflows embedding earlier snapshots remain unchanged. The editor supports deterministic string/Boolean function graphs only. Graph-function source assets preserve canvas node placement, labels/comments, sections, and wire presentation in a versioned Studio authoring envelope; this presentation does not change the function's executable content hash. Legacy graph-function files without the envelope open with an automatically generated layout because their former layout was not stored. Changes to workflow definition and layout remain local to the editor until you choose **Save source file**. Only the active folder tab listens for filesystem notifications and revalidates the full project snapshot every 20 seconds to catch missed events. Inactive folders stop watching and revalidate when you return to their tabs. If it detects a change, a clean editor offers **Reload project files**. With unsaved edits, Studio preserves the editor buffer and offers **Discard local edits and reload folder**; choose it only when you want to abandon those edits. Reload rereads and validates the folder at the time you click. If a Git checkout is temporarily inconsistent, the conflict remains visible until the folder is valid again. Save operations reject stale content they detect, but external writers are not locked out. Closing a tab with unsaved edits asks you to keep it open or explicitly discard those edits. To execute, open a workflow and choose **Run workflow**; a dialog collects its input and parameter overrides, and the editor only enables it for saved, executable source with no unsaved or detected external changes. Studio rereads and validates the whole manifest and verifies the expected manifest and asset hashes before capturing the run. To test an earlier state, create a restore point, keep a workflow selected, and choose **Test selected workflow** beside that restore point. This runs the workflow from that point's validated archive without restoring or changing the active project. The run viewer shows live events and replay data. Runs and their definition/layout/source hashes remain in the Studio host's run store, not in the project folder. Inputs and parameter values are recorded as audit evidence and are not a place for secrets. The folder editor does not publish catalog revisions; project-specific catalog routes return HTTP 409 rather than falling through to an unrelated SQLite catalog. The Projects list can download a validated source snapshot directly from the folder. You can also export selected saved workflows as a consumer `.vawpkg`; the release is separate from editable source. See [project folders and workspaces](project-workspaces.md) for file format and migration stages.

Use **Project tools** in a folder Explorer header to open consumer packaging and local restore-point controls. Folder workflows use the same compact canvas, node inspector, **Runs**, **Output**, and **Problems** layout; **Run workflow** opens their test input dialog and **Inspect execution** opens recorded graph evidence. For an invalid saved draft, **Run workflow** stays available so the attempted run can select **Problems** and explain the block; it never starts execution until the graph is valid. Saving a workflow updates its existing document tab.

The folder workspace uses a dedicated IDE titlebar and activity rail, a Visual Studio–style Explorer with read-only `vaw.project.json`, open document tabs, a graph editor, and a docked **Runs**, **Issues**, and **Output** panel. Right-click the root or any folder and choose **New file** to create a workflow, agent, skill, function, or Markdown document; **New subfolder** adds nested directories. Right-click files or folders for cut, copy, paste, duplicate, rename/move, and delete actions. Folders can follow your domain structure rather than the default `workflows/`, `agents/`, `skills/`, and `functions/` roots. Markdown is ordinary editable `.md` project documentation and is not included in consumer workflow packages. It opens in the locally bundled Monaco editor with Markdown syntax highlighting and theme-aware colors. Use **Save Markdown** or `Ctrl+S` / `Cmd+S`; if Monaco fails to load, the editor offers a plain-text fallback. The editor bundle loads only when a Markdown file opens and does not use a CDN. Executable source files use `.workflow`, `.agent`, `.skill`, and `.function` extensions; their contents remain JSON and old `.json` files continue to open. Use **Add node** to reveal the node library when needed. On narrow screens, the project switcher, **Studio settings**, and the theme selector remain available in the titlebar. Project-owned MCP connection manifests are not implemented yet: MCP endpoints, stdio launch details, credentials, and grants are configured by the Studio or consuming host, outside the project folder.

## Build a consumer release

Open a folder project and save any workflow edits you want to include. In **Build consumer package**, select one or more workflow entry points and choose **Download selected workflows**. Only selected workflows must pass executable validation, so unfinished drafts elsewhere in the project stay out of the release. The archive includes a manifest, validated workflow packages, layouts, embedded snapshots, and their derived host requirements. It does not include project source files that were not selected, Git data, `.vaw/`, MCP endpoints, model credentials, grants, or run history. Review prompts and other user-authored workflow text before sharing.

A consuming service loads the archive with `WorkflowProjectPackageJson.Read` or uses the standalone [WorkflowService sample](../samples/WorkflowService/README.md). The consumer chooses an entry workflow and resolves provider, MCP, and node requirements using services it has registered. The host must still authorize tools; a package requirement never grants access. This format validates integrity but is not signed, does not install assemblies or services, and does not activate a deployment. For local testing, Studio can run a selected saved workflow or test one from a local restore point.

To convert a catalog-backed project into a Git folder, first stop Studio, then run `dotnet run --project src/VisualAgentWorkflow.Studio -- --migrate-project-to-folder <project-id> <new-folder>`. Include `--environment Development` when required by your local launch setup, and configure `WorkflowStudio:DataDirectory`/`WorkflowStudio__DataDirectory` the same way as Studio. The destination parent must exist and the destination folder itself must not. The command preserves the project ID and current editable workflow drafts, layouts, skills, profiles, and graph functions. Published/revision/audit history and run data stay in Studio's data directory; credentials and MCP grants are not copied. Studio and the command share an exclusive data-directory lock; the command fails if a Studio process is still using that directory. If Studio stops during migration, its next startup validates the journal and completes a published migration before opening writable project services.

## Restore a project folder snapshot

In an open folder project, use **Create restore point** after saving or discarding editor changes. Studio validates the complete current manifest and its indexed files, then saves a content-addressed copy under `.vaw/snapshots/`. The first restore point adds `/.vaw/` to the project `.gitignore`, preserving existing ignore rules. A project can hold up to 20 restore points and 256 MiB; Studio does not silently remove old points when the limit is reached.

Choose **Preview restore** to compare the captured manifest with the current source. Studio blocks restore while there are unsaved editor changes or an external folder conflict. Confirm **Restore this project snapshot** to switch the manifest to that validated source state. Studio keeps newer immutable files and unindexed files on disk, so inspect the change in Git afterward. To test without changing the active source, select a workflow and click **Test selected workflow** beside a valid restore point. Studio loads and verifies the point in memory, then runs that captured definition and layout; it does not restore the active manifest. The resulting audit data goes to the Studio host run store. You can delete individual restore points from the list or remove `.vaw/` in your file manager; doing so never changes the project manifest or source files. Corrupt or missing sidecar data disables local restores and snapshot tests but does not prevent opening or exporting project source.

## Build workflows for your own service

Studio can act as an IDE for workflows that your own application will run. You can also embed the designer in your application or use the engine without a designer. These are independent integration choices.

Today, you can export reviewed workflow definitions/packages and use the lower-level .NET execution libraries from host code. A standalone service/worker sample and shared local-runtime DI registration are implemented; Studio is not required for execution. Stable NuGet distribution and a production hosting SDK remain planned. See [service integration](service-integration.md) for available entry points and host responsibilities. The controls below describe authoring and testing in the development Studio, not deploying an authenticated production service.

## Start the app

From the repository root, with the SDK pinned by `global.json` installed:

```sh
dotnet restore --locked-mode
dotnet build --no-restore --configuration Release
dotnet run --project src/VisualAgentWorkflow.Studio --configuration Release --no-build -- --environment Development
```

Open the loopback address printed by the host, normally port 5099. Keep the backend process running while executing workflows. Closing the browser leaves backend runs running; stopping the backend interrupts unfinished runs.

## Configure model providers

Open **Studio settings → Model connections** and select **Add connection**. Enter a stable connection ID, display name, served model ID, endpoint, and timeout. For LM Studio, use `http://localhost:1234/v1`, enable **Allow unencrypted HTTP for this endpoint**, and leave the API key empty unless authentication is enabled. The same form works with Unsloth and other OpenAI-compatible APIs. Context-window and input/output/cache pricing fields are optional observability metadata. Select **Test connection** to send a fixed short request to the configured model before saving, then select **Add connection**. The test limits output to one token and may incur a small provider charge. Existing connections have their own **Test connection** action. Testing does not save changes. The key is protected in local Studio storage and is never returned to the settings page.

To change a connection, select **Edit connection** on its card and save. Keep the ID unchanged: agent nodes and profiles reference that ID, so the edited model, endpoint, default timeout, and metadata apply to future runs using that connection. A configured agent-node timeout takes priority; the connection timeout is used only when the node timeout is blank. Leave the API-key field blank to keep the stored key, or choose **Remove the saved API key** to clear it. Run history records the model descriptor and reported token usage used at the time; playback does not make live calls. The graph viewer displays attempted model turns, regular, cache, and reasoning token counts (reasoning is included in output totals), context usage when a context window is configured, and estimated cost when all observed priced components are configured. During an in-flight model request, it labels context usage from the last completed response as stale until new usage arrives. It also shows the number of recorded host compactions. The execution-evidence table includes each event's local time to milliseconds, with the exact timestamp and offset available on the time value. The cost is an estimate based on reported usage, not the provider's bill. Delete a connection only when you are ready for references to fail provider preflight until they are updated or the connection is restored. Settings are served by the loopback-only unauthenticated development Studio; do not expose it through a public proxy. See [provider settings and runtime bounds](model-providers.md).

## Create and edit a workflow

1. Select **New workflow**. The draft begins with connected Input and Output nodes. Give it a descriptive **Workflow name**; the generated workflow ID stays stable for references and integrations. Existing workflows without a saved name continue to display their ID until named.
2. Search the **Node library**, then click an action to insert it after the selected node. The insertion hint names the path; select **Insert on output** for a condition's true or false arm. Click insertion opens space downstream. Drag an action onto the canvas to choose its position, or onto a wire to insert on that path.
3. Right-click the canvas, a node, or a wire for **Graph actions**. You can also focus the canvas and press Space or Shift+F10, search for an action, and use arrow keys to navigate. Drag an output socket to a compatible input socket to connect or rewire it; the target pin highlights when it can accept the connection. Reconnecting a pin replaces any wire already attached to that input or output, and the change can be undone. Right-click a wire and choose **Disconnect wire** to remove it. Drag an output socket onto empty canvas to create a step on that exact path. Escape cancels the menu. Select a node to configure it in the properties panel. Change a processing node's operation using its dropdown. Use **Move up**, **Move down**, or **Remove** to change the connected execution sequence. Use **Undo edit** and **Redo edit** to recover local edits.

The editor's left rail contains a **Workflow map** with one selectable entry per graph node and the searchable **Node library** below it. Selecting a map entry also selects that node on the canvas and opens its properties. At the bottom of the editor, **Run**, **Versions**, and **Issues** tabs expose published-run controls, version management, and the current validation report. Run a published version from the Run tab; **Open run inspector** switches to the separate viewer for recorded history and execution evidence. The tab does not execute an unsaved draft. In the run inspector, the recorded-events table and each node's **View events** dialog show the event's invocation and connection identities alongside its node and scope, making repeated activations and actual path evidence distinguishable during playback.

Drafts may be incomplete while you edit. A visible **Workflow validation issues** panel lists the exact unresolved paths and messages; **Save draft** remains available, while publish and activate controls stay disabled until all issues are fixed. Runtime and published-run APIs validate before execution, so an incomplete draft cannot run. Definition, layout, and package exports are also disabled until the graph validates.
4. For an agent, set **System instructions**, choose a provider, and select its requested tools. Set **Maximum output tokens** from 1 to 16,384 for each response; existing workflows default to 1,024. In schema 1.29 or later, choose **Workflow input** as the source to make this limit configurable at run time; only integer parameters with an in-range default are offered. The run override is checked against the same range before execution starts. Optionally set **Maximum total tokens** from 1 to 100,000 across the agent and its delegated profiles, or bind it to an integer workflow input in schema 1.29+. This requires provider-reported usage; without it the configured budget fails closed. A prompt may itself exceed the limit, and parallel requests already in flight can finish beyond it, so this is not a billing guarantee. Set **Maximum model turns** to a positive integer (default 8), or enter **-1** for unlimited turns; **0** is invalid. The first model response counts as turn one, including tool-call rounds. Timeout and token limits can still bound execution. Optionally set **Agent timeout in seconds** to any positive whole number. This per-node timeout takes priority over the model connection's default timeout; leave it blank to use that connection default. Enable **Require a structured result** to require one `submit_result` call with a success/failure status and JSON object payload. The agent output becomes JSON; connect it to **Select JSON property** at `/status`, then to a Condition to route `success`, `reported_failure`, `turns_exhausted`, `tokens_exhausted`, `token_usage_unavailable`, `timeout`, `invalid_result`, `provider_error`, or `tool_error`. Host cancellation still cancels the run. The endpoint or model may enforce a lower output-token cap. Providers that advertise reasoning controls show **Reasoning effort**. **Off** asks for no reasoning, while **Provider default** leaves the choice to the endpoint; compatible endpoints may ignore either preference. Use **Customize user message** to edit one readable text template. Type `{{` to open matching value suggestions, then use Tab and Enter or click a suggestion. `{{input}}` inserts the incoming graph value; `{{parameter:ID}}` inserts a declared workflow parameter. Write a backslash before `{{` for literal opening braces. The preview uses sample input and parameter defaults; each run renders actual values before the model call. The demonstration provider explicitly does not interpret instructions. External providers send system instructions, the resolved user message, and assigned tool results to the configured endpoint. Selecting a tool does not grant access; the backend checks policy when it runs.
5. To let the agent choose a workflow path, edit **Agent-selected execution routes** in schema 1.30 or later. Enter one route per line as `stable-id | Label | Description`, then wire each labeled execution output pin to its destination. The provider must support function calling. The agent chooses using the internal `select_route` function; its route is followed only after the agent succeeds. A missing or invalid choice fails the agent without activating a path. Removing a route leaves its old connection as a visible validation issue; drafts can be saved, but publishing and running remain blocked until you rewire or remove that connection.
6. Select **Save draft** to persist definition and layout. Unsaved changes block switching workflows and publication until saved or discarded.

### Try the typed graph preview

The preview is an opt-in starting point for a blank draft with only the connected Input and Output nodes. Select **Start typed graph preview** in the node library. It keeps the existing data connection and adds a separate execution activation from Input to Output. The library then offers **String constant** and **Concatenate text**. Add both without relying on automatic wiring, edit the constant value in its properties, then connect Input's string output and the constant to the two concatenation inputs, and connect the concatenation output to Output's data input. Rewire the original Input-to-Output data edge to the concatenation output. The execution wire remains a separate route; it does not carry the string value.

#### Add a direct MCP tool node

From a valid linear typed graph, select **Enable direct MCP tools** in the node library. New graphs use schema 1.37, which exposes host-discovered MCP bindings under **MCP tools**. Select a tool to add an unconnected node, then connect its `then` execution pin to the next tool or Output, and connect its `out` data pin to the next node's data input. The node displays one incoming data pin per supported top-level tool argument, such as `path · string` and `maxBytes · integer`; schema 1.40 also supports finite `number` pins supplied by a Number constant. Connect constants, workflow values, or other typed producers to supply variables. Select the node and open **Inputs** in the properties pane to see live, display-only descriptions for matching tool properties; unavailable or stale bindings simply omit that guidance. The properties pane also accepts explicit static values for fallback/default arguments. JSON Schema `default` annotations are not applied automatically. Schema 1.36 workflows retain the legacy single `in` pin and JSON-object behavior. The node invokes the tool directly; no Agent or model turn is involved.

On a valid schema 1.37 direct-MCP graph, choose **Enable number graph values** to move to schema 1.40. This adds the **Number constant** and allows top-level MCP `number` properties to be connected as typed pins; it does not add implicit integer conversion, numeric operators, or nested numeric pins.

On a valid schema 1.40 number-pin graph, choose **Enable workflow number parameters** to promote it to schema 1.41. A finite `number` workflow parameter can then feed a typed Workflow value node connected to an existing persisted MCP `number` pin. The value is sent as a JSON number and recorded as typed evidence; no string/number coercion, numeric operators, nested numeric pins, or generic numeric workflow output is added.

The direct node's properties pane is generated from the selected tool's supported JSON Schema, including scalar values, enums, nested JSON values, arrays, required/optional fields, and field descriptions. Values are workflow data, not secret storage. The host broker still checks the node grant, pinned contract, live schema, and invocation limits on every call; contract drift fails closed. Nested objects and arrays remain JSON pins in schema 1.37. Direct MCP graphs are intentionally straight-line deterministic graphs; they do not add direct tools to existing Agent, branch, parallel, loop or approval graphs.

#### Add run-scoped variables

On a blank valid typed graph, choose **Enable run-scoped variables**. Schema 1.44
adds a **Workflow variables** editor for non-secret string, Boolean, integer, and
finite-number declarations. Add a variable with a stable ID, display name,
default, description, and type, then add **Get variable** or **Set variable**
from the Variables section of the node picker. Bind each node to a declaration
in its properties pane and wire both execution and typed value pins explicitly.
Each workflow run receives an isolated store; reads and writes are recorded as
`variable.get` and `variable.set` evidence with a write version. In the run
inspector, scrubbing a recorded prefix reconstructs the selected variable's
value, version, and read/write history from those events only; it never reruns
the graph. This first slice is deliberately linear and rejects parallel, Sequence, collaboration,
async, graph-function, and shared child-workflow variable writes. On a valid
schema 1.44 variable graph, schema 1.45 adds one explicit bounded loop with a
single linear body. It can repeat Set/Get operations up to 16 times; variable
evidence records the non-negative loop iteration and playback reconstructs the
recorded prefix without rerunning the body. Schema 1.45 remains outside
checkpoint recovery, and parallel, Sequence, collaboration, and shared-child
variable state remain unsupported.

When that explicit data graph is valid, choose **Enable Boolean Branch preview** in the node library. Schema 1.24 exposes **Compare strings**, **Boolean Branch**, and **Terminate workflow**. Connect two string sources into Compare strings, connect its Boolean output to the Branch condition input, and wire Input execution to Branch. Route Branch `true` to Output and `false` to a Terminate node whose outcome is **Failure**. Connect a string data source to Output's data input. The comparison uses ordinal, case-sensitive equality: no whitespace removal, case folding, or text-to-Boolean conversion occurs. Branch starts one route only. Its selected output and the pure values it read are recorded in the run audit, and playback never reevaluates the graph. Schema 1.26 supports bounded nested Branch nodes and reconvergent routes; see the next subsection for its topology and validation rules.

For Boolean logic, first validate the schema 1.24 branch graph, then choose **Enable Boolean primitives**. This upgrades the definition to schema 1.25 without changing existing connections. The **Values** section now offers **Boolean constant** (defaults to `false`, configurable in node properties) and **Boolean NOT**. Add either node unconnected, then wire compatible Boolean data pins yourself. Constants preserve an explicit `true` or `false` value in the workflow definition. NOT inverts its connected Boolean input. Both nodes are pure: they run only when a downstream node requests their value, and their typed results are recorded for playback. There is no implicit conversion from strings.

To build a larger decision graph, validate the schema 1.25 draft, then choose **Enable branch topologies**. This upgrades to schema 1.26 without changing existing edges. You can now add up to eight Boolean Branch nodes and 16 Terminate nodes. Wire each Branch's `true` and `false` execution sockets to another Branch, Output, or Terminate. An Output or Terminate may receive multiple mutually exclusive incoming routes, so branches can converge without a Merge node. Each reached node runs once, regardless of how many alternative routes enter it. The graph must be acyclic and have a structural path to Output; validation cannot determine whether data-dependent predicates will select that path at runtime. Therefore a graph can validate but still terminate on every run for the values it receives. Terminate nodes can independently mark their exit successful or failed. The Studio records the selected arm, activated edge, evaluated Boolean values, and terminal outcome for playback.

For signed integer values, first validate a schema 1.30 agent graph, then choose **Enable integer graph values**. Schema 1.31 adds an **Integer constant**, **Add integers**, **Compare integers**, and a typed **Workflow value**. Integer pins represent signed 64-bit values; add is checked and an overflow fails the run. Schema 1.42 adds the bounded **Add numbers** pure operator to number-enabled direct-MCP graphs; it accepts only finite `number` pins and fails if IEEE-754 addition produces a non-finite result. Select a numeric constant to edit its value. A workflow-value pin matches the selected parameter's type; number parameters are available in schema 1.41/1.42 number-enabled graphs. Data wires never activate nodes, and Boolean Branch routes still control execution. The Output node returns integer and Boolean values as invariant text and records the typed value in its audit event. Older workflow schemas keep their original string behavior and are never silently upgraded.

From a valid schema 1.31 integer graph, choose **Enable string-to-integer conversion** to move to schema 1.39. Add **String to integer** from the Values library and connect its `in · string` pin to the Input or another string producer, then connect `out · integer` to an integer node or Output. The node is lazy and deterministic: `+42`, `-42`, leading zeros, and the signed 64-bit bounds are accepted; whitespace, decimal syntax, non-ASCII digits, and overflow fail with a recorded reason. This is an explicit conversion, not implicit coercion. Schema 1.38 is reserved for the bounded Sequence contract in the Blueprint parity roadmap, and the conversion is not available inside graph-function bodies.

### Ordered Sequence nodes

Schema 1.38 workflows can use **Sequence** to activate two to four execution outputs in authored order. Select the node to rename outputs, move them up or down, add a connected output, or remove one while at least two remain. Output IDs and execution wires remain stable when labels or order change. Schema 1.38 routes each output directly to the workflow Output node and records the authored Sequence/output/connection identity.

Schema 1.43 is the first downstream-path promotion. Each Sequence output can start one bounded, acyclic, disjoint path of direct MCP tool nodes, and every path must end at the same Output barrier. Paths are dispatched in authored order but may complete in a different order; the workflow does not complete until every admitted path reaches the barrier. Shared intermediate nodes, branches, loops, nested workflows, Agent nodes, and unconnected paths are rejected by validation. The Studio may save the invalid draft, but publish and run admission remain blocked until the topology is repaired. Schema 1.38 definitions are not silently promoted or reinterpreted.

From a valid schema 1.43 path graph, choose **Enable terminal uppercase paths** to opt into schema 1.47. This adds one typed **Sequence uppercase** step at the end of a path after any direct MCP tools. It accepts and returns `string`, has explicit `execute` and `then` pins, and must connect directly to Output. The step is deterministic and preserves the normal Sequence lifecycle/evidence; it does not add a generic expression language or allow Agents, child workflows, branches, or loops in the same path.

When a path is invalid, the Problems tab names the ordered Sequence output and its stable `then.<outputId>` pin. It also identifies the unsupported path node or competing path owner and states the repair constraint, such as connecting exactly one direct MCP path, keeping paths disjoint, or giving each tool exactly one execution successor. These diagnostics are editor guidance only: saving preserves the draft for repair, while publish and run still require a valid schema 1.43 topology.

Save the draft as usual. A valid graph can run and publish; disconnected or incorrectly typed pins remain editable but block both. In Run inspector, the recorded cursor highlights each evaluated data wire and the selected pure node shows its recorded value. Sequence path runs record the output identity and execution connection for each path; the Sequence node displays each path's recorded dispatched, completed, failed, cancelled, or skipped state, while the selected-node inspector also shows the connection identity. Playback reads the stored events without recalculating the graph. This remains a deliberately narrow explicit graph subset; richer Agent paths and general Blueprint control composition are still planned. See [deterministic visual programming](graph-values.md) for the planned expansion.

### Sequence Agent topology proof seam

The platform includes a diagnostic-only Core analyzer for a future Sequence
path that ends in one plain-text Agent. It is not a Studio feature or a
runnable schema: schema 1.43 still accepts direct MCP paths only. See [the
topology analyzer decision](decisions/0021-sequence-agent-topology-analyzer.md)
for the exact bounded shape and promotion gates.

### Create and reuse pure graph functions

Open **Function library** from the top navigation. Select **New function** to start with a string input, a fixed `!` suffix, text concatenation, and a string output. The function ID stays stable across revisions; each saved version is immutable. Set its name, description, and folder, then edit the interface by adding, renaming, removing, or changing the type of named input and output pins. Current interface types are `string`, `boolean`, and `integer`.

Use the Function nodes palette to add string constants and operators, Boolean constants and NOT, integer constants and operators, or finite number constants and **Add numbers**. Function input/output ports can be typed as `number`. Added nodes are unconnected. Drag compatible data sockets to build a data-only graph. Select a node to edit its constant or remove it. The validation panel explains missing boundaries, incompatible pins, cycles, or other issues; saving is disabled until the function is valid. Function bodies are limited to 64 nodes, 128 connections, 16 inputs and 16 outputs, and 16,384 characters per string. Control flow, MCP calls, agents, external effects, and arbitrary code are not supported in functions.

Choose **Save immutable function version**. To make a change, select **New version from this function** on a saved revision, edit the copy, and save the next version. Folder changes organize the local library without changing the function content hash. Deleting a library entry does not change any workflow that already embeds its snapshot.

To call a function from a workflow, first validate a Boolean-primitive workflow and choose **Enable pure graph functions**. The node library lists saved function revisions. Add the exact revision you need, then connect compatible data pins to its named input/output sockets. The call node contains the immutable definition and hash; no service-side function catalog lookup occurs. Publish and export the workflow normally. The consumer only needs the workflow package and any ordinary provider/MCP registrations used by the rest of that workflow. Function library CRUD is local to this Studio; standalone function-package import/export and draft collaboration are not implemented yet.

### Insert a reusable pure graph template

Catalog-backed projects can store immutable pure graph-template revisions separately from callable graph functions. When a template catalog is available, open the node library's **Templates** section and choose the exact revision to insert. Studio opens a binding dialog rather than guessing connections: select one compatible existing data output for every template input and one compatible existing data input for every template output. Existing single incoming data connections are called out as replacements, and the preview reports the nodes, connections, and replacements that will be applied. **Insert template** performs the validated expansion as one editor change, so Undo removes the whole insertion. Folder-backed projects and runtime execution do not consume this catalog; use a pinned graph-function or child-workflow node when you need a runtime reuse boundary.

### Expose pure graph functions as agent tools

1. Create and validate the pure function you want the agent to use. Give it a clear name and description and define named inputs and outputs; those become the tool contract the model sees.
2. In a valid schema 1.27 workflow, choose **Enable agent function tools**. Select the Agent node and use **Graph function tools** in its properties to assign the exact saved function revision. The agent receives only the selected revisions, up to eight; adding another function revision to the library does not silently expose it.
3. Connect the Agent node's execution pins as usual. The function call result is returned to the model as a JSON object with the declared outputs; the Agent node's data output remains the agent's final response for downstream workflow nodes.

The runtime validates arguments and rejects undeclared inputs. Calls are limited to 16 per agent invocation, 1,024 aggregate evaluated graph nodes, and 65,536 aggregate input and output characters. Audit records capture the exact function hash, inputs, outputs, evaluated values, and failures. Run playback displays these records without calling the model or reevaluating the function. Graph functions are pure: they cannot use the agent's MCP tools or perform external I/O. Use an explicitly assigned MCP tool for external services.

### Define reusable workflow inputs

1. Expand **Workflow parameters** above the graph. Add a parameter with a stable ID, display name, default value, and optional description that explains how to use it. The description appears as help text when editing or running the published workflow. Choose Text, Integer, Number, True/false, or Choice. Choice values are comma-separated and the default must be one of them. IDs accept letters, digits, dashes, and underscores; values are limited to 16,384 characters.
2. Add a **Workflow value** node from the **Inputs** section of the node library. Select which parameter it reads in the node properties. The node replaces its incoming string with that parameter and passes the selected value to the next node, so the data path stays visible in the graph.
3. Save and publish the definition. The parameter schema and defaults travel with the workflow package. When running a published version, edit the displayed parameter values to override defaults for that run. The effective values are captured in the run header and shown in the playback inspector.

Typed parameters remain immutable workflow configuration; they do not create mutable graph variables or expose credentials. A choice parameter with `default,off,low,medium,high` can be assigned to an agent's **Reasoning effort** setting. In schema 1.29+, integer parameters with valid defaults can also configure the agent's **Maximum output tokens** and **Maximum total tokens**. These run-time bindings do not permit changing provider connections, tools, skills, endpoints, credentials, or host grants. Run overrides never alter the published definition, are validated against type, choices, and the bound setting's range before execution, and appear in audit/playback. Because the local run store records inputs and parameter values, do not enter secrets or sensitive information.

### Build text with a template node

Add **Text template** from the node library on the selected path. The node starts by passing through its incoming text. In the properties panel, enter ordinary text and insert `{{input}}` for that incoming value or `{{parameter:ID}}` for a declared workflow parameter. Suggestions appear as you type `{{`; the preview shows sample input and parameter defaults. Write `\{{` for literal opening braces. Save the workflow and run it with an input and optional parameter overrides; the node's rendered output and outgoing transfer are recorded for replay. Templates are structured literal/reference parts, limited to 64 parts and 8,192 characters of stored text; rendering is bounded to 16,384 characters. There is no expression evaluation, model call, or side effect in this node.

### Select and project JSON input

Select the **Input** node and choose **Use JSON input and add a value selector**. The Studio changes that entry input to JSON and inserts a selector before the existing string path. Set the selector's **JSON Pointer** using RFC 6901 syntax, such as `/customer/name` or `/items/0/id`. A selected JSON string becomes plain text; numbers, booleans, null, objects, and arrays become compact JSON text. The selector accepts at most 16 path segments and 1,024 pointer characters; workflow JSON input is bounded to 16,384 characters and a maximum nesting depth of 32. Its string output can feed existing text, agent, tool, and output nodes.

To build a smaller JSON object, first use **Use JSON input and add a value selector** to switch the Input to JSON. Select Input and add **Project JSON fields** from the node library; it is inserted before the initial selector. Select the projection node and add rows in its properties: each row names an output property and gives the JSON Pointer for the source value. For example, map `customerName` to `/customer/name` and `total` to `/orders/0/amount`; the node emits `{"customerName":"Ada","total":42}`. It supports 1–16 uniquely named fields. Choose a value kind for each field. Scalar kinds validate the selected value. Choose **object** to open a property mapper: add output properties, give each a JSON Pointer relative to the selected object, choose its value kind, and mark it optional if missing input should omit it. Choose **array** to define how each item is mapped; its item pointer is relative to that item. Nested contracts can map objects inside arrays and arrays inside objects. Only declared object properties appear in the result. A missing required pointer or mismatched value kind fails at the projection node and records a safe path/type explanation without echoing the selected value. `any` preserves the selected value. Contracts are limited to depth 8, 128 schema nodes, 16 properties at each object, 64 items per array, and 16,384 characters of mapping configuration. Keep the selector after the projection to convert a chosen value to text for an agent or string tool. Remove that selector if the workflow should return the projected JSON object directly. Input and resulting JSON are each bounded to 16,384 characters; JSON nesting is limited to 32. Invalid JSON or a pointer that does not resolve fails the run and is visible in recorded evidence. Removing the original input selector restores text input when the selector is the input's only JSON consumer.

### Configure MCP servers and skills

Open **Studio settings → MCP connections** (the MCP library). Choose **Streamable HTTP** for a remote/local HTTP server, or **Local process (stdio)** to have Studio launch a local executable. HTTP requires HTTPS except on loopback; its optional bearer token is stored encrypted. For stdio, enter the executable and its arguments on separate lines, with one argument per line. You can set a working directory and explicit process environment values; values are encrypted in Studio settings. Studio starts the process as the same OS user, without a shell and without inheriting the Studio environment. This is not sandboxed: only configure commands and packages you trust, and do not put secrets in arguments.

For example, Brave Search's current MCP server defaults to stdio. Install Node.js 22 or newer, get a Brave Search API key, then create a stdio connection with executable `npx`, arguments `-y`, `@brave/brave-search-mcp-server`, `--transport`, and `stdio` (one per line), and environment variable `BRAVE_API_KEY` set to your key. Leave working directory blank unless needed. Keep the server process local to the Studio host; VAW starts it when discovering or invoking tools. The API key is for Brave and belongs in the server environment field, not the HTTP bearer-token field. See [Brave's setup documentation](https://github.com/brave/brave-search-mcp-server#configuration).

Enter a stable server ID, display name, and optional folder, then select **Test connection & discover tools**. This opens the transport, lists tools, and reports how many have compatible schemas; it neither saves the connection nor enables tools. Discovery shows compatible tools and an **Excluded tools and compatibility reasons** list. Review each compatible tool's description, input summary, schema hash, and description hash. Check the tools this Studio may offer, then select **Save server and selected tools**. Each configured server also has a **Test connection** action that reopens its stored HTTP or stdio transport, checks tool discovery, and reports supported/excluded counts without changing settings. Failure messages distinguish common causes such as missing executables or working directories, authentication rejection, unreachable endpoints, initialization timeouts, and protocol/tool-discovery errors. Error details are sanitized; process stderr, environment values, and credentials are not displayed. Return to the designer, select **Refresh MCP tools**, and expand **Tool details** beside a tool on the agent node to review it before assignment. The description is provided to the model and its hash is pinned independently from the input/output schema; older workflow bindings without a description pin remain readable. Tool arguments may use nested bounded objects and arrays of `string`, `integer`, `number`, and `boolean` values. Required/optional properties, scalar enums, string/array length bounds, string patterns, and numeric minimum/maximum values are enforced by the broker. Patterns must use the .NET non-backtracking regex subset, be at most 256 characters, and match within a 50 ms limit. JSON Schema `default` is annotation-only: `default: null` does not make a string or integer argument nullable or optional; requiredness comes from the schema's `required` list. If `additionalProperties` is omitted, Studio treats the object as closed. Arrays without explicit bounds are capped at 64 items. Other limits are 32 declared properties per object, depth 8, 8,192 characters per string, 1,024 values, 65,536 characters per call, and 16,384 characters per schema. Unsupported JSON Schema keywords, unions, references, and non-text results are not supported. For an explicit MCP node, ordinary input text is supplied as the `text` argument; to pass another supported argument shape, provide a JSON object string matching the tool's input summary. A changed pinned schema or pinned description prevents the tool from running; rediscover and review before republishing. Removing a server does not remove workflow requirements. A fresh process is started for stdio discovery and each invocation, with a 30-second operation timeout; `npx` can add startup delay, especially on first use. Stdio clients negotiate the MCP protocol automatically: they try the current discover protocol and fall back for servers that use the older initialize handshake. Streamable HTTP currently stays on protocol `2025-11-25`.

Select **Skill library** to create a text-only skill revision. Give it an ID, version, name, folder, and instructions. Save another version to change the instructions; moving folders does not change identity. In the designer, select an agent and check the exact skill revisions under **Skills**. The selected text is embedded in the workflow when it is saved and exported. An imported workflow can be reviewed as a draft without installing a Studio skill library. The runtime appends only that agent's selected skill text to its system instructions; it does not interpret skill text as a permission grant. Deleting a skill from the Studio library does not change published versions.

A consuming service needs its own model-provider and MCP registrations matching the workflow's provider IDs and tool contract hashes, plus its own tool authorization policy. It does not need the Studio's skill library because the assigned text is in the package. Endpoints, bearer tokens, and host grants do not travel with exports. See [agent capability libraries](agent-capability-libraries.md) for the portability model and current limits.

### Design reusable subagents

Open **Agent Designer** in the top navigation. Create a profile with a stable ID and version, instructions, a model connection, and optional reasoning/output-token settings. Select only the MCP tools and skill revisions the specialist needs. To let profiles coordinate when assigned together, add shared **Coordination channels** such as `research` or `review`, one channel ID per line. A profile can join up to eight channels; use lowercase letters, numbers, dots, hyphens, or underscores. Save the profile. To change a saved profile, use **New version** and save the revised settings as a new immutable revision. Folders only organize the local Studio library. The profile keeps the model connection ID, so editing that connection changes the model used by future profile runs without changing the profile version.

Back in a workflow, select a parent agent node and add the desired exact profile versions under **Subagents**. The workflow embeds those profile snapshots and skill text. The parent model can call only the profiles assigned to that node. Each child receives the task as its user message and can use only its own profile tools. MCP calls must also pass the consuming host's grant for the workflow node; package import never grants access.

The current bound allows four assigned profiles and four child executions per parent invocation, with one delegation level and a 16,384-character task. When at least two profiles are assigned, the parent also sees a team tool that sends one shared task to all assigned profiles concurrently and returns named JSON results. Individual calls and team members share the four-execution limit. If any member fails, the team cancels remaining members where possible and returns no partial aggregate; any already completed external action remains completed.

The parent model chooses which assigned delegate to call and when, up to four child executions per parent invocation. Sequential delegate turns share a coordination-channel board for that parent invocation. A profile with channel memberships receives `channel_send` and `channel_read` tools only for those channels. Profiles assigned the same ID can exchange append-only messages between turns. The parallel team tool still runs every assigned profile concurrently, but gets a separate board isolated from sequential turns and other team calls. Each message is limited to 4,000 characters, each channel to 32 messages, and each board to 64. Every send and read is recorded under the child invocation, including the exact messages returned to the agent, so playback can show what it saw without re-running the model. A profile cannot read a channel it did not join. When configured, the parent agent's aggregate token budget is shared with delegated profiles; simultaneous calls already in flight can finish beyond the threshold. Persistent agent memory and aggregate time budgets are not implemented. See [agent profiles and bounded delegation](agent-profiles.md) and [agent results and budgets](agent-results-and-budgets.md).

## Organize the canvas

Drag a node header to place its card. Arrow keys move it by 8 logical units; Shift increases the step to 40. Drag a selection rectangle over empty canvas to select several nodes; hold Ctrl/Cmd or Shift while dragging to add nodes to the selection. Ctrl/Cmd-click or Shift-click a node toggles it in the selection. Drag any selected node to move the selected group together. Drag empty background to select; middle-drag to pan across the expanded canvas. **Reset view** returns to the graph origin at 100% zoom, while **Fit graph** fits and centers the nodes. These view controls do not save graph edits. **Arrange nodes** restores generated positions, retains annotations and sections, and clears reroute points so old routes do not cut across the new arrangement. Undo restores the previous positions and routes.

Select a card to inspect its properties; compact cards show summaries instead of editing forms. Use **Label, comment and position** in that panel for annotations. Long comments show a small diagonal expand/collapse icon at the bottom-right of the rendered node comment; short comments omit it. The expanded/collapsed state is saved with the workflow layout, and the full text remains available through the custom tooltip when the compact preview truncates. The library, inspector, and lower details pane can be resized with their splitter handles; those pane sizes are local to this Studio browser and **Studio settings → Reset editor layout** restores defaults. Open **Labels, comments, sections, and wire routing** below the canvas for grouping and wire controls. Select **Node to organize** to edit a label, comment, or X/Y coordinates. Labels never replace stable node IDs, and comments are text rather than executable agent instructions.

To create a labeled section, enter **New section label**, check its member nodes, then select **Group selected nodes**. Drag the section header to move all members in one edit. Rename the section or use **Ungroup** in the inspector. Membership is explicit; simply placing a card inside a frame does not join it. A node belongs to one section at a time.

Double-click a wire to add a reroute point, or select a wire in the inspector and use **Add reroute point**. Move points with the mouse, arrow keys, or coordinate fields. **Pinned angle** fixes the tangent; curved wires also accept custom degrees. **Right-angle** style constrains bends to orthogonal segments. **Reset wire route** removes the routing points without deleting the connection. These edits share the same undo/redo history as other draft changes.

**Fullscreen graph** expands the canvas, library, properties and toolbar using the browser fullscreen API. Escape or **Exit fullscreen graph** returns to the page and restores focus. Fullscreen requires browser/iframe permission; a rejection leaves the inline editor available with an explanation. View switching, selection, fit, and fullscreen do not alter a saved workflow or stop execution. Within the graph, Ctrl/Cmd+S saves; Ctrl/Cmd+Z undoes and Ctrl/Cmd+Y or Ctrl/Cmd+Shift+Z redoes when outside a text field. Delete removes an eligible selected processing node. Required terminals and merges cannot be deleted independently. Delete on a condition opens a confirmation for removing its entire conditional block.

Use **Find workflow** to filter saved IDs; the selected workflow remains available even when it does not match.

## Run and inspect

Select **Run inspector** for run controls and history; **Designer** returns to the authoring canvas with local edits preserved. Starting a published run opens the inspector automatically. Use **Filter recorded runs** to find a workflow, status, or run identity.

For a quick test, choose a workflow in **Quick template run**, enter **Input**, and select **Start independent run**. For a saved workflow, enter **Published run input** and select **Run selected version**. This uses the selected immutable revision, including when the draft has unsaved edits.

Select a run under **Recorded runs**. Click a node's execution card to inspect its recorded input/output. Each node also has **View events**, which opens a modal filtered to that node and any nested scope beneath it at the current playback position. Failed and cancelled nodes show a recorded cause when one is available; cancellation is visually distinct from failure. Agent usage is available under **Usage details** so the terminal state remains easy to scan. Active nodes show their latest recorded activity, such as waiting for a model response or calling an MCP tool; playback shows activity only up to the selected event. **Previous event**, **Next event**, the recorded-position slider, and **Follow latest** control playback. The graph/details and lower evidence panes are resizable with pointer or keyboard input, and their widths/heights are persisted in Studio-local layout settings. Thick dashed teal wires correspond to recorded transfer events; moving cards cannot fabricate execution evidence. Historical viewing makes no live model/tool calls. If a tool succeeds but the model supplies no final text, the agent node uses the successful tool result as its output and records this fallback in the `agent.completed` event. Check that event and the tool result before retrying side-effecting workflows. **Cancel selected run** explicitly requests cancellation; closing the page does not.

## Pause and resume a run

Select a nonterminal run under **Recorded runs**, then choose **Pause selected run**. Wait for `paused`: an in-flight node and its tool/model operations finish first. **Resume selected run** continues the same run; when the status is `pausing`, it withdraws the pending pause. **Cancel selected run** also works while paused.

For fast workflows, check **Start paused** before **Start independent run**, or **Start published run paused** before **Run selected version**. No node executes until resumed. Closing or reloading the page preserves the backend pause state. Other runs can execute while one is paused, within the 32-context admission limit.

Playback shows **State at recorded position** separately from the latest status. Scrubbing over a recorded pause is observation only. Host restart interrupts unfinished runs; it cannot resume their old continuation. See [run-control guarantees and API](run-control.md).

## Reuse a section or published workflow

1. Create a named section containing consecutive processing nodes. Exclude input/output terminals.
2. Open **Reusable workflows**, choose **Section to save**, enter a unique **Reusable workflow ID**, and select **Save section as reusable draft**. This creates a separate draft and leaves the current workflow unchanged.
3. Save any current edits, open that new draft in **Saved workflow**, review it, and publish it. Reusable workflows use the same explicit version lifecycle as other workflows.
4. In a consumer workflow, open **Reusable workflows** and choose **Reusable workflow**, an exact **Reusable version**, and **Insert workflow after**.
5. Review the listed requirements, then select **Insert published workflow**. Use **Undo edit** if needed, then save and publish the consumer explicitly.
6. To keep the source graph reusable as a separate unit, select an exact child version and choose **Call pinned workflow version**. The call embeds that immutable child release. Its input and output pins match the child’s declared `string` or `json` boundaries, so connect matching types. In the call node’s properties, map compatible parameters from the parent workflow into child parameters; unmapped child parameters use the published defaults.
7. To inspect a child while staying in the parent, open **Reusable workflows**, select its call under **Inspect or upgrade a pinned call**, and expand **Inspect pinned child graph**. The view is read-only and shows the embedded definition; Studio uses the saved child layout when available or generates one for inspection. When reviewing an upgrade, expand **Inspect target child graph** to inspect the candidate without replacing the current pin.
7. To change a call to another publication, select its node under **Inspect or upgrade a pinned call**. Review the child definition and dependency changes, then choose **Apply upgrade to draft**. Compatible parameter mappings remain; incompatible mappings are shown and removed so the child uses its new default. The edit is undoable and affects only the parent draft. Save and publish it explicitly to activate the new pin.

Inserted steps have fresh identities and retain their copied annotations, MCP tool contracts, and stable model connection IDs. They show which source/version they came from. Later source publications do not rewrite existing copies, and edits to a copy do not change the source. A pinned call instead keeps the complete child definition in its node and runs it under the parent run’s audit identity. Playback shows child events under that call node without re-executing them. Host authorization still applies to child nodes; a parent does not automatically inherit child tools or vice versa.

## Share and recover local work

Open **Import / export definition**. Use **Copy workflow package into JSON editor** or **Download workflow package** to share the full definition/layout and declared requirements. To import, create or select a draft, paste the package into **Workflow JSON**, and choose **Import package into draft**. Checksum/manifest validation detects mismatched contents; it does not authenticate the sender. Review user-authored text and requirements before sharing or executing.

Package import keeps the current workflow ID, stages one undoable local edit, and requires explicit save/publication. It grants no tools, installs no code, and starts no run. Missing registrations are listed; even a matching registration still needs host policy permission. Existing executable JSON and separate layout sidecar downloads/imports remain available. Layouts validate node/connection references against the current definition.

The catalog and run history survive normal host restarts. Hosts can choose file or SQLite run storage; changing that setting selects a separate history and does not migrate runs. See [storage configuration and upgrade notes](run-storage.md). Unsaved browser edits do not. Interrupted Studio runs are recorded as interrupted rather than automatically retried. A separate [consumer checkpoint API](checkpoint-recovery.md) supports explicit recovery of deterministic saved suspensions; Studio has no checkpoint recovery controls. A stale tool contract, unavailable provider, denied grant, or oversized input can fail a run; inspect its evidence and correct the draft/configuration rather than assuming it was rolled back or retried.

Workflow calls currently allow three nested levels and 1,024 expanded nodes, `string` or `json` input/output boundaries, compatible parent-to-child parameter mappings, explicit revision upgrades with dependency review and undo, and a read-only child graph view. Unmapped child parameters keep their defaults. Child workflows may request approval before an MCP tool; playback shows the parent call, nested path, and executing child revision. Host grants remain independent, and concurrent approval-bearing parallel branches are blocked. Collaborative editing, credentialed live-provider qualification, durable approvals, arbitrary-crash/external-call recovery, and production authentication remain future work. Follow the [nested workflow call contract](nested-workflows.md), [approvals](approvals.md), [roadmap](roadmap.md), and [graph controls](graph-editor.md) for current limits.

## Execute from your own service

Export a reviewed workflow package and deploy it with an operator-owned revision/content pin. The [standalone service sample](../samples/WorkflowService/README.md) shows direct and queued invocation without opening Studio, plus node-scoped host grants and local run evidence. Its commands are documented in the sample; no catalog or browser is required. It remains a single-process development runtime without crash recovery.

Service developers can use `AddLocalWorkflowRuntime` to register the same backend runtime in a .NET Generic Host, then resolve invocation/control services. See the [local hosting API](hosting-sdk.md) for lifecycle, dependency registration and current source-consumption limits. Studio controls are unchanged by this helper.

To provide deterministic custom MCP tools in a consumer service, host them in an operator-reviewed, digest-pinned container and register the tool with `ContainerMcpToolRegistration`. Then add its logical binding to the workflow node and add a matching node-specific host grant. A worker may optionally be configured with a subset of the same node's MCP bindings, allowing it to request those tools through the broker without receiving credentials or network access. The container can also load one approved, versioned extension assembly pinned by SHA-256. The registration does not transfer image identity or permission through workflow packages. This consumer-host configuration is not yet available in Studio's MCP connection form. See [containerized MCP workers](extension-workers.md) and [isolated .NET extensions](extension-assemblies.md) for the code sample, resource limits, isolation proof, and current restrictions.

## Observe a consumer service

When a consumer has enabled its authorized observation endpoint and a Studio operator has configured a named source, choose **Observe a consumer service**, select **Consumer source**, then **Connect to consumer**. Choose a run to inspect live state, node payloads and recorded playback. The connection is read-only; **Disconnect observation** and closing the browser do not change consumer execution. The **Recovery assessment** panel explains unsettled work and checkpoint disposition at the latest evidence cursor, independently of recorded playback. It offers no retry/recovery controls, and eligibility still requires fresh validation by an exclusive host. A connection failure explicitly marks the retained last received evidence and suppresses the old assessment. See [assessment meanings](run-reconciliation.md). See [configuration, embedding and limits](observation.md).

## Add a conditional path

Add a **Condition** from the node library to create a single unconnected branch node. Configure its operator and operand, then connect its input and route the true and false output pins independently. Library additions do not make implicit connections; use **Add node after** or a wire context menu when you explicitly want insertion. Each route can continue to the workflow Output, another condition, or a success/failure **Terminate workflow** node. A merge is needed only when routes should rejoin before shared work. Output accepts multiple alternative routes, and only the selected route executes. Incomplete graphs can be saved as drafts with issues shown; resolve them before publish or run. **Arrange nodes** provides a starting layout, and **Undo edit** reverses edits. The viewer records **Selected output: true/false**, highlights actual transfers, and shows termination or failure; playback makes no calls. To remove a decision block, select a condition and choose **Remove conditional block…** when the selected graph forms a recognized complete block. See [conditions, bounds and current editing limits](conditional-graphs.md) and [workflow termination](workflow-termination.md).
## Add a bounded loop

On a connected string path, select an output and choose **Bounded loop** in the **Flow** section of the node library. The inserted loop has a **Loop body** anchor; select it and add the processing nodes, agent, or MCP tool that should repeat. The final body connection returns to the loop input, while the loop’s **done** pin continues the original path. Select the loop and configure **Continue while**, its match text, and a **Maximum iterations** value from 1 to 16. Predicates use ordinal, case-sensitive text matching.

The initial text reaches the body only when the predicate matches. Each completed body pass returns its result to the loop, where the predicate is tested again. A false predicate or the maximum cap sends the current text through **done** and completes normally. The run journal records each iteration start and completion and whether the predicate or cap stopped the loop. Playback shows the recorded values and does not rerun the body. Pausing takes effect at a node boundary. Tools and agents inside the body may run more than once; external side effects are not rolled back.

Only one loop is supported per workflow in this version, with a single linear body and no other control nodes or JSON paths. To remove it, select the loop and choose **Remove loop and run body once**; its body steps remain on the path exactly once. See [bounded loop semantics and limits](loop-graphs.md).

## Run two paths in parallel

Select a connected string path and choose **Parallel block** from the node library. Studio adds a visible **Parallel fork**, two named **Parallel branch** anchors, and a **Parallel join**. Both branches receive the same string and execute concurrently. Add text transforms, agent nodes, or MCP tools after either branch anchor; keep branch 1 connected to join input `branch_1` and branch 2 to `branch_2`. The join waits for both and emits a JSON object containing both results. Studio inserts a JSON selector to preserve an existing downstream string path, or changes the terminal Output to JSON when the block ends the workflow. Select the whole object with an empty JSON Pointer or choose `/branch_1` or `/branch_2` to continue as text.

A workflow may contain up to four sequential blocks, each with two named branches. To add another one, select a string connection after the preceding block’s JSON selector and insert **Parallel block** again; schema 1.20 records this capability. Branch paths must be simple and complete; they cannot contain another control block, condition, approval, or nested join. The validator rejects parallel blocks placed on independent condition paths. If one branch fails or is cancelled, there is no joined result. A completed side effect in the other branch is not rolled back. Agent and MCP operations on both branches may be active at the same time. Each joined JSON result is capped at 16,384 characters. To remove a block, select any fork, branch, or join inside it and choose **Remove parallel block…**. Review the affected node list before confirming; Studio reconnects the original path, and **Undo edit** restores the block. See [parallel graph behavior and limits](parallel-graphs.md).

## Create configurable parallel branches

To start a schema 1.32 region, first use a valid schema 1.31 graph that begins with Input activating an Agent or Boolean Branch. The graph’s Output must still return the input text. Choose the **Number of branches** from 2 to 8 in the **Parallel agent workflow** panel, then select **Create parallel workflow**. Studio atomically inserts the fork, named branch anchors, and matching join. The join’s named JSON result becomes the workflow Output. Save, inspect the fork’s **Branch order, labels, and count** controls to rename captions, move branches up or down, or add another branch up to the eight-branch limit.

Branch IDs and wire pins stay stable when captions change or branches move. To add work, add Agent nodes from the node library, disconnect the anchor-to-join wire, and wire the anchor through its Agent nodes to the join pin with the same branch ID. Schema 1.32 branches use a straight Agent sequence and cannot contain conditions, loops, nested forks, or standalone MCP nodes. **Add branch** creates a connected empty branch and matching fork/join pins. **Move up** and **Move down** change display/pin order without changing IDs or wires. **Remove empty branch** is enabled only when the selected branch contains no Agent nodes and at least two branches will remain; remove or move the branch’s Agent nodes first. These edits participate in Undo/Redo. Removing the complete region restores the input-to-output path and is undoable. Runtime execution fans branches out concurrently, joins them into a bounded JSON object keyed by branch ID, and fails without a partial object if any branch fails. Join object keys are serialized by stable ID order, not branch completion order. See [parallel graph behavior and limits](parallel-graphs.md).

## Route within a parallel branch

Schema 1.34 permits one Boolean Branch inside each static schema 1.32 fork branch. Add **Boolean Branch** from the Flow node library while editing a schema 1.32 graph; Studio upgrades the draft to schema 1.34. Connect a Boolean data value to the Branch condition, then connect both **true** and **false** execution outputs to nodes within the same owning branch. Both outcomes must eventually reach that branch's join input, which keeps its original stable branch ID. A route may send both outcomes to one shared Agent node: only the selected outcome activates it, so this is exclusive local reconvergence rather than a second fan-in.

Each branch can contain at most one Boolean Branch. Conditions cannot escape to another branch or bypass the matching join. Loops, approvals, merges, nested/repeated forks, and cross-branch paths remain invalid. Incomplete routes stay saveable as drafts with validation issues; publish and run require a complete valid topology. The runner records the selected port, stable branch ID, fork activation, and actual execution-connection activation. It runs only the selected Agent route and still emits one result per branch at the all-or-nothing join. Schema 1.33 collaboration branches remain linear; conditional routing there is deferred. See [branch-local parallel routing](parallel-branch-routing.md).

## Add shared communication between parallel Agents

Schema 1.33 adds one message rendezvous to an existing configurable parallel region. It supports one publish-before/read-after barrier across 2–8 branches. Start with a schema 1.32 graph that already has its matching fork, branch anchors, and join.

1. In the node library's **Flow** section, choose **Parallel rendezvous**. Studio adds exactly one unconnected node; it does not add other nodes or change your wires. Select the new node in **Node to organize**.
2. In **Region binding**, select the matching fork and join, enter one shared channel ID per line, optionally enter a positive barrier timeout, and choose **Apply region and branch pins**. Studio creates a matching input and output pin for each stable fork branch ID.
3. Under **Per-branch Agent grants**, add a grant on each branch that will communicate. Choose the exact Agent node, choose **Publish before rendezvous** or **Read after rendezvous**, and name one or more channels that you declared. Publish Agents must be before the barrier; read Agents must be after it. Agents without a grant do not receive collaboration tools, and profile delegates do not inherit a parent's grant.
4. Wire each branch anchor through its publish Agents to the rendezvous input with the same branch ID. Wire each matching rendezvous output through its read Agents to the corresponding join input. The join emits the branch results as JSON after all branches arrive.
5. Save the draft as you work. Studio keeps incomplete or miswired collaboration graphs editable and lists the issues; publication and execution stay disabled until all topology and grant issues are resolved. Undo/Redo covers the authoring edits. Publish only after the graph has one complete path through the barrier on every branch.

During a run, an authorized publish Agent can append bounded messages to its assigned channels. It cannot read messages until the rendezvous releases one immutable snapshot. An authorized read Agent receives only its assigned channels from that snapshot. The barrier uses the workflow's timeout when set, or the finite timeout supplied by the host. Playback shows the recorded sends, release, reads, arrivals, and any later abort without calling a model or MCP server. A branch failure after release prevents the join result but does not roll back completed external effects. This first version does not support loops, nested or repeated rendezvous, post-release writes, retries, or interrupted-run recovery. See [the collaboration contract](parallel-agent-collaboration.md).

Schema 1.35 supports two ordered collaboration phases in a static 2–8 branch region. Phase-1 publishers write to the first phase board before rendezvous 1. After all branches arrive, phase-1 readers can read its frozen snapshot and phase-2 publishers can write to a separate board. Rendezvous 2 waits for every branch and freezes a second snapshot for phase-2 readers before branches reach the join. Use a distinct Agent node for each granted phase and role; each Agent receives only its exact node, phase, role, and channel access. One finite deadline starts when the fork is admitted and covers both waits. Channel, message, and snapshot-byte limits apply cumulatively across the region. A timeout, cancellation, branch failure, or join failure aborts the region and suppresses the joined result while preserving already recorded snapshots, reads, and external effects. Playback shows each phase and the evidence recorded before an abort. In Studio, open the first rendezvous in a valid schema-1.33 collaboration region and choose **Upgrade to two phases**. Studio adds and assigns one unwired second rendezvous, preserving each existing Agent grant as a phase-1 publish or read operation. Review each branch grant and set its phase, role, and allowed channel IDs. Add a separate Agent node for each operation. Then explicitly connect every branch through rendezvous 1, rendezvous 2, and its matching join input; Studio never wires these paths during upgrade. An incomplete 1.35 draft can be saved and reopened with validation diagnostics, while publish and run are unavailable until the topology and grants validate. Removing either rendezvous removes the collaboration region and both barriers as one undoable edit. Schema-1.33 retains its original one-barrier grants and authoring flow. See [two-phase parallel Agent collaboration](parallel-agent-collaboration-phases.md).

## Require review before an MCP call

On an MCP tool card, choose **Require approval before tool**, edit the inserted approval prompt, then save and publish. A selected path reaching it shows `waiting-approval`. Review **Recorded action approval** and **Exact tool input**, then choose **Approve recorded action** or **Reject recorded action**. Reloading the browser preserves the same request. Pausing and approving are separate: approval cannot resume a paused run, and resume cannot approve a call. Remote read-only observation and historical playback show evidence without decision controls. Host restart interrupts the pending continuation. See [exact-action approval semantics](approvals.md).
