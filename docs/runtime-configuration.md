# Runtime providers and capability boundaries

The Studio remains a local development host. These registration points are for trusted host code; workflow authors cannot supply executable commands, endpoint URLs, credentials, or factories through definitions.

## MCP bindings

`McpToolRegistration` maps a logical alias to a server/tool and a cancellation-aware `McpClient` connection factory. Registrations default to non-read-only and are denied by the initial broker; an administrator must explicitly designate supported read-only registrations and provide an `IToolAuthorizationPolicy`. Remote provisioning, credentials, side-effect approvals, and arbitrary argument schemas are not supplied by this prototype.

`ExplicitToolAuthorizationPolicy` accepts grants by workflow ID, node ID, and binding ID. A definition's tool requirements are checked independently and never grant authority. A production host still needs authenticated workspace/principal policy and trusted invocation identity; these local grant records are not an authentication system.

The Studio MCP library can connect to Streamable HTTP endpoints or launch an operator-configured local stdio process. HTTP connections enforce HTTPS except for loopback and store bearer tokens in protected local settings. Stdio commands, structured arguments, working directory, and explicitly entered environment values remain in host-local settings; explicit environment values are protected. The process starts with a small SDK-provided base environment and the configured values, without inheriting the Studio process environment. VAW does not use a shell and does not sandbox stdio processes: they run with the Studio OS user's privileges, so only configure trusted executables and packages. Discovery and each tool invocation start a fresh process and have a 30-second operation timeout.

The built-in Studio also launches its own known fixture entry point over stdio and registers deterministic text, integer, and nested-object/array tools. `--mcp-demo-server` is an internal fixture entry point, not a public HTTP endpoint or a mechanism for workflow-selected executables. Consumer hosts can implement their own MCP registration and policy; workflow definitions never provide connection or process-launch settings.

For a separately built worker image, consumer host code can use `ContainerMcpToolRegistration.Create` with a registry `@sha256:` digest or local immutable image ID. It launches a fresh Docker container for each MCP connection with network, inherited environment, writable root, and Linux capabilities disabled plus resource limits. Optionally set `CapabilityBindingIds` to create a private read-only Unix-socket channel for selected node-assigned MCP tools; each request is reauthorized by the normal broker. A versioned extension artifact can also be pinned by assembly SHA-256 and loaded from the fixed image path inside the worker. Brokered capabilities and assembly workers require a local Linux Docker Engine and cannot chain through another capability-enabled worker. `AllowInvocation` only exposes the registration; node-specific `IToolAuthorizationPolicy` grants still govern each call. No arbitrary executable, environment, network, or Docker argument fields are accepted from workflow definitions. See [containerized MCP workers](extension-workers.md) and [isolated .NET extensions](extension-assemblies.md) for the contract and isolation proof.

Agent MCP tool contracts support nested closed objects and arrays of `string`, `integer`, `number`, or `boolean` values, with required/optional properties, scalar enums, string/array length bounds, and numeric minimum/maximum constraints. Bounds cap each object at 32 properties, nesting at depth 8, arrays at 64 items, strings at 8,192 characters, arguments at 1,024 values and 65,536 characters, and schemas at 16,384 characters. Unsupported JSON Schema keywords, open objects, unions, references, and non-text results are rejected. Ordinary input to a direct MCP graph node maps to the conventional string `text` argument; a JSON object string can provide the supported typed arguments. Definitions pin the actual tool name/input/output schema fingerprint returned during discovery. Schema fingerprints detect contract drift; they cannot freeze a remote implementation's behavior.

## Agent providers

`AgentProviderRegistration` pairs an `AgentProviderDescriptor` with a factory returning an owned `Microsoft.Extensions.AI.IChatClient`. The executor disposes that client workflow after the invocation, so return a fresh client or an ownership-aware wrapper rather than an application-wide singleton that must remain alive.

Construct `AgentNodeExecutor` with the registrations and the same node tool broker used by direct MCP nodes. Register it as `IAgentNodeExecutor` for execution and `IAgentProviderCatalog` for authoring choices. `LocalWorkflowRuntime` accepts both interfaces through its constructor. The Studio's DI composition in `Program.cs` demonstrates this with the deterministic fixture.

A workflow stores provider ID/version, instructions, and explicit tool requirements. Host code owns model client construction, identity/authentication, model settings, network destinations, and credentials. Tool functions exposed to the agent are broker delegates; do not replace them with raw `McpClientTool` instances, which would bypass platform authorization and recording.

The deterministic provider calls the first assigned function once or returns `Demo agent: <input>`. Instructions are passed through the real agent API and captured but are intentionally not interpreted by this fixture. Provider descriptors and recorded lifecycle events label the fixture as deterministic. No external model provider is enabled automatically. The optional [OpenAI adapter](model-providers.md) now supplies host-configured factories with protocol-fixture verification; credentialed live-service qualification has not been run.

Production integrations must validate the chosen provider/package versions, cancellation behavior, persistence requirements, output constraints, sensitive-data handling, and authentication. Provider ID/version pins a host contract, not reproducible external model behavior. Historical playback continues to use saved evidence without provider or tool calls.
